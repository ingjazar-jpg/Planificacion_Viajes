## 1. Objetivo

Consolidar la base compartida del frontend existente para habilitar la implementación de los módulos funcionales con una arquitectura consistente, reutilizable, accesible y conectada al backend.

El bloque debe entregar una aplicación navegable con un selector global de período funcional, un cliente HTTP centralizado, manejo uniforme de errores y estado compartido disponible para las pantallas.

No se reconstruirá desde cero el shell ya existente ni se implementarán en este bloque las funcionalidades completas de Dashboard, calendario, actividades, presupuesto, gastos, informes o restauración.

## 2. Contexto y estado inicial

El frontend utiliza React 19, Vite, JavaScript/JSX, HTML5 y CSS3. La navegación inicial y el shell ya existen en la rama de trabajo.

Archivos existentes comprobados:

- `frontend/src/App.jsx`
- `frontend/src/main.jsx`
- `frontend/src/layouts/AppLayout.jsx`
- `frontend/src/components/layout/Sidebar.jsx`
- `frontend/src/components/layout/Topbar.jsx`
- `frontend/src/components/layout/MobileNavigation.jsx`
- `frontend/src/config/navigation.js`
- `frontend/src/styles/global.css`
- `frontend/src/styles/tokens.css`
- Páginas placeholder bajo `frontend/src/features/`.

El shell actual ya presenta Sidebar, Topbar, navegación móvil y seis secciones. El selector de período y el acceso a alertas aparecen deshabilitados mientras se completa su integración. Las páginas funcionales siguen siendo placeholders.

La implementación deberá inspeccionar los archivos actuales y extenderlos con cambios mínimos y compatibles. No se asumirá que las rutas o componentes propuestos en documentos de planificación ya existen.

## 6. Contratos de integración

### 6.1 Endpoint de períodos

- Método: GET.
- Ruta: `/api/v1/periods`.
- Parámetros: opcionales `page` y `page_size`, que deben enviarse conjuntamente si se utilizan.
- FE-001 no necesita paginación y consultará el listado sin parámetros.
- Respuesta exitosa: objeto con propiedad `data`, arreglo de períodos.
- Error: objeto `error` con `code`, `message` y `details`.

Ejemplo de respuesta:

```json
{
  "data": [
    {
      "id": "UUID",
      "year": 2026,
      "name": "Vacaciones decembrinas 2026",
      "start_date": "2026-12-20",
      "end_date": "2027-01-10",
      "created_at": "2026-11-14T10:00:00-05:00"
    }
  ]
}
```

El backend devuelve los períodos ordenados por año y fecha de creación descendentes. El frontend no volverá a ordenar ni inferirá cuál es el último período: seleccionará el primer elemento de la respuesta.

### 6.2 Configuración de URL

El cliente HTTP utilizará una configuración centralizada de origen/base URL compatible con el entorno local. La ruta contractual de recursos conservará el prefijo `/api/v1`.

El host del backend será exclusivamente `localhost`, conforme a API-001 y ARCH-001. El puerto y la forma concreta de inyectar la configuración se verificarán contra la configuración real de ejecución del backend durante la implementación; no se fijará un puerto supuesto en esta especificación.

La configuración no expondrá secretos ni habilitará servicios externos.

### 6.3 Manejo de respuestas y errores

- Respuestas JSON exitosas se devolverán al consumidor con su estructura contractual.
- Respuestas HTTP 204 se tratarán sin intentar analizar un cuerpo JSON.
- Las respuestas de error se normalizarán conservando `code`, `message` y `details`.
- Si el servidor no está disponible o no se puede interpretar la respuesta, se generará un error de transporte comprensible, sin exponer trazas internas.
- El cliente no transformará ni redondeará importes o valores de dominio.
- Los componentes no harán llamadas HTTP directas fuera del servicio centralizado.

## 7. Modelo de estado global

El contexto del período expondrá, como mínimo:

| Propiedad | Tipo | Descripción |
|---|---|---|
| `periods` | Array | Períodos recibidos desde API. |
| `selectedPeriodId` | UUID o null | Identificador del período seleccionado. |
| `selectedPeriod` | Objeto o null | Período completo seleccionado. |
| `isLoading` | Boolean | Indica carga inicial o recarga. |
| `error` | Error normalizado o null | Error de carga, si existe. |
| `refreshPeriods` | Función | Vuelve a consultar el listado. |
| `selectPeriod` | Función | Cambia la selección a un período existente. |

Reglas:

1. La consulta inicial se ejecuta al montar el proveedor global.
2. Si la respuesta contiene períodos y no existe selección, se selecciona el primer elemento.
3. Si el usuario selecciona otro período, el contexto actualiza `selectedPeriodId` y `selectedPeriod`.
4. La selección no se guarda en localStorage, sessionStorage ni otro almacenamiento del navegador.
5. Al recargar o abrir nuevamente la aplicación, se selecciona el período más reciente devuelto por el backend.
6. Si una recarga ya tiene un período seleccionado y este continúa en la respuesta, se conserva la selección durante esa sesión.
7. Si el período seleccionado ya no aparece en la respuesta, se selecciona el primero; si la lista queda vacía, la selección pasa a null.
8. Un identificador que no corresponda a un período de la lista no podrá establecerse mediante `selectPeriod`.
9. Los módulos consumidores no mantendrán copias independientes del período global.
10. El contexto no contendrá ni duplicará reglas de negocio.

## 8. Arquitectura y organización

Se mantendrá la estructura existente cuando sea compatible. La organización lógica esperada es:

- `app/`: composición y proveedores globales.
- `components/layout/`: Sidebar, Topbar y navegación móvil.
- `components/common/`: componentes reutilizables de estado y presentación.
- `context/`: contexto global de período.
- `hooks/`: hooks consumidores del contexto.
- `services/api/`: cliente HTTP, normalización de errores y servicio de períodos.
- `features/`: módulos funcionales.
- `layouts/`: layout principal.
- `styles/`: tokens y estilos globales.

La estructura es una guía lógica. No se moverán archivos existentes únicamente para hacer coincidir nombres de carpetas. Los imports, pruebas y shell deberán seguir funcionando.

## 9. Reglas de interfaz

- El selector global permanecerá disponible en las seis secciones.
- Mostrará nombre y año, con etiqueta accesible.
- Durante la carga inicial se indicará que los períodos se están consultando y se evitará una selección ficticia.
- Sin períodos, mostrará estado vacío y acceso contextual a Actividades, sin ejecutar una operación inexistente.
- Ante error, mostrará un mensaje y opción de reintento.
- La navegación activa conservará `aria-current="page"`.
- El menú móvil podrá operarse por teclado y dispondrá de nombres accesibles.
- Los estados no dependerán exclusivamente del color.
- El diseño deberá funcionar desde 360 px y no producir desplazamiento horizontal global.
- Se respetarán los tokens de UI-001 y el CSS existente.
- El acceso a alertas permanecerá como elemento visual no funcional o se presentará según el estado definido por UI-001 hasta su implementación en FE-002; no se simularán contadores ni alertas.

## 11. Estrategia de pruebas

Se añadirán o actualizarán pruebas para cubrir:

1. Renderizado del layout y proveedores globales.
2. Navegación por las seis secciones.
3. Apertura, cierre y selección del menú móvil.
4. Solicitud de períodos al iniciar.
5. Selección del período más reciente según orden del backend.
6. Cambio de período y propagación al contexto.
7. Conservación de selección durante recarga si el período sigue existiendo.
8. Sustitución de selección si el período desaparece.
9. Estado vacío cuando la respuesta contiene un arreglo vacío.
10. Error HTTP con estructura contractual.
11. Error de transporte y reintento.
12. Tratamiento de respuesta sin cuerpo.
13. Ausencia de persistencia en localStorage/sessionStorage.
14. Accesibilidad básica del selector y navegación.
15. Build de producción.

Las pruebas de frontend usarán mocks de red deterministas. La integración real se comprobará contra FastAPI después de implementar y sincronizar el bloque.
