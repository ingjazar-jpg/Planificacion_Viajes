## 1. Objetivo

Implementar la pantalla **Gestión de datos** para consultar el catálogo de copias de seguridad semanales y restaurar una copia válida mediante confirmación explícita. Completar la integración del frontend con los módulos ya validados y ejecutar la regresión transversal necesaria para cerrar el frontend.

El frontend consumirá exclusivamente los endpoints existentes en API-001 §5.9. No accederá directamente a archivos JSON, manifiestos, rutas físicas ni referencias internas de respaldos.

## 2. Alcance

### 2.1 Incluido

1. Consulta del catálogo de copias semanales disponibles.
2. Presentación de fecha de creación, identificador y estado de validación.
3. Tratamiento de catálogo vacío, carga, error y reintento.
4. Habilitación de restauración únicamente para copias cuyo estado informado sea `valid`.
5. Advertencia y confirmación explícita antes de restaurar.
6. Envío del contrato de restauración existente.
7. Presentación del resultado y recarga del contexto global y los datos de la aplicación tras una restauración exitosa.
8. Pruebas de servicios, componentes, integración y regresión de FE-001 a FE-006.
9. Revisión transversal responsive, accesibilidad, errores y consistencia de navegación.

### 2.2 Fuera de alcance

- Crear copias manualmente desde la interfaz.
- Eliminar copias desde la interfaz.
- Configurar frecuencia o retención.
- Consultar, listar, descargar o restaurar copias `pre_write`.
- Mostrar rutas físicas, `file_reference`, manifiestos o metadatos internos.
- Leer o escribir `datos_vacaciones.json` desde el frontend.
- Añadir endpoints, parámetros, campos o reglas de negocio.
- Añadir operaciones administrativas distintas de las definidas en UI-001.
- Cambiar la lógica backend de backups, persistencia o restauración.

### 3.2 Consulta del catálogo

**Contrato:** `GET /api/v1/backups`

- Sin parámetros de consulta.
- Respuesta HTTP 200 con `data`.
- Devuelve exclusivamente copias `weekly`, ordenadas por `created_at` descendente.
- Máximo 15 registros; no admite paginación.
- Cada elemento contiene exactamente los campos contractuales relevantes para la interfaz: `backup_id`, `created_at`, `type` y `validation_status`.
- `validation_status`: `valid`, `invalid` o `not_validated`.
- `invalid` y `not_validated` no son restaurables desde la interfaz.
- El listado presenta el último estado registrado; consultar el listado no valida nuevamente el contenido de cada archivo.
- Un catálogo sin copias responde HTTP 200 con `data: []`.
- No se exponen `file_reference`, rutas físicas ni identificadores `pre_write`.

### 3.3 Restauración

**Contrato:** `POST /api/v1/backups/restore`

Request contractual:

```json
{
  "backup_id": "UUID",
  "confirmed": true
}
```

- `backup_id` es UUID y debe corresponder a una copia semanal registrada.
- `confirmed` es obligatorio y debe ser exactamente `true`.
- El frontend no envía rutas ni referencias físicas.
- El backend vuelve a validar la integridad y estructura de la copia antes de reemplazar los datos actuales.
- El backend genera el respaldo preventivo necesario, ejecuta la restauración segura y valida el resultado.
- Una copia inválida no reemplaza los datos actuales.
- La respuesta exitosa HTTP 200 incluye `data.status`, `data.backup_id`, `data.restored_at` y `data.message`.

Errores contractuales:

| HTTP | Código | Tratamiento de interfaz |
|---:|---|---|
| 404 | `BACKUP_NOT_FOUND` | Informar que la copia ya no está disponible; permitir volver al catálogo. |
| 409 | `BACKUP_NOT_RESTORABLE` | Informar que la copia no es válida o no puede restaurarse; no presentar éxito. |
| 422 | `RESTORE_CONFIRMATION_REQUIRED` | Tratar como solicitud no confirmada/ inválida; no presentar éxito. |
| 500 | `BACKUP_RESTORE_FAILED` | Informar fallo controlado; no presentar éxito. |

Todos los errores mantienen la envoltura uniforme de API-001 §4. La interfaz no mostrará trazas ni detalles técnicos internos.

### 3.4 Comportamiento normativo después de restaurar

Conforme a API-DEC-038, tras una respuesta exitosa:

1. Volver a consultar los períodos disponibles.
2. Actualizar el selector global.
3. Conservar el período seleccionado si todavía existe.
4. Si ya no existe, seleccionar el último período creado.
5. Recargar los datos de la aplicación usando el contexto actualizado.

Cancelar el diálogo no ejecuta la operación ni envía la solicitud.

## 4. Requisitos funcionales preliminares

Los siguientes requisitos son una base de refinement y están sujetos a revisión:

### 4.1 Catálogo

- **RF-001.** La pantalla Gestión de datos consultará el catálogo mediante `GET /backups`, sin parámetros.
- **RF-002.** La interfaz mostrará las copias en el orden recibido por el backend y no reordenará el catálogo.
- **RF-003.** Cada elemento mostrará fecha de creación, identificador de copia y estado de validación.
- **RF-004.** La fecha se presentará de forma legible, respetando el timestamp con zona horaria recibido.
- **RF-005.** El estado `valid` se identificará como disponible para restauración.
- **RF-006.** Los estados `invalid` y `not_validated` se identificarán como no restaurables y su acción de restauración estará deshabilitada.
- **RF-007.** No se mostrarán controles de creación o eliminación de copias ni información de respaldos preventivos.
- **RF-008.** Si el catálogo está vacío, se mostrará un estado vacío informativo sin ofrecer una acción de restauración.
- **RF-009.** La consulta tendrá estados diferenciados de carga, error, vacío y contenido.
- **RF-010.** Ante error de consulta, se ofrecerá reintento explícito.
- **RF-011.** La interfaz no simulará ni calculará el estado de validación; presentará el valor recibido del backend.

### 4.2 Confirmación y restauración

- **RF-012.** La restauración solo podrá iniciarse desde una copia cuyo `validation_status` recibido sea `valid`.
- **RF-013.** Antes de enviar la solicitud, la interfaz mostrará un diálogo de advertencia que identifique la copia seleccionada y comunique que los datos actuales serán reemplazados por los datos de esa copia.
- **RF-014.** El diálogo ofrecerá una acción explícita para confirmar y otra para cancelar.
- **RF-015.** Cancelar cerrará el diálogo sin enviar ninguna solicitud.
- **RF-016.** Confirmar enviará exclusivamente `backup_id` y `confirmed: true` en el cuerpo contractual.
- **RF-017.** Mientras la restauración esté en curso, se evitarán solicitudes duplicadas y se impedirá cerrar o confirmar nuevamente el diálogo.
- **RF-018.** La interfaz no mostrará porcentajes de progreso que el backend no proporciona.
- **RF-019.** El éxito solo se comunicará después de recibir una respuesta exitosa de restauración.
- **RF-020.** Los errores 404, 409, 422 y 500 se presentarán con mensajes comprensibles, sin exponer detalles internos.
- **RF-021.** Después de una restauración exitosa se aplicará el flujo de recarga de períodos y datos definido por API-001 §5.9 y API-DEC-038.
- **RF-022.** La recarga no modificará ni recreará registros desde el frontend; se limitará a consultar el estado persistido que devuelve el backend.
- **RF-023.** El frontend no inferirá que una restauración falló si el endpoint ya confirmó éxito. El resultado de la restauración y el resultado de la recarga del contexto se presentarán como estados independientes.
- **RF-033.** El catálogo se consultará automáticamente cada vez que el usuario entre en la pantalla Gestión de datos, incluso si ya se había consultado en una visita anterior.
- **RF-034.** No habrá actualización periódica automática ni botón manual de refresco del catálogo. Si la consulta falla, se ofrecerá reintentar explícitamente.
- **RF-035.** Si la restauración devuelve 404 o 409, la interfaz volverá a consultar el catálogo para reflejar que la copia desapareció o cambió de estado. Esta consulta nunca repetirá la restauración.
- **RF-036.** Después de una restauración exitosa no se volverá a consultar `GET /backups`, porque la operación no modifica el catálogo de copias semanales. El resultado exitoso confirma que la copia seleccionada superó la validación del backend.
- **RF-037.** Después del HTTP 200 de restauración, la interfaz mostrará el éxito de la operación antes de iniciar la recarga del contexto. Un fallo de recarga no cambiará ni invalidará ese resultado.
- **RF-038.** La recarga posterior consultará primero los períodos y determinará el período activo. Luego forzará la actualización de los datos de todos los módulos funcionales mediante sus consultas GET existentes, incluso si el UUID del período activo se conserva.
- **RF-039.** Si el período activo anterior ya no existe, se seleccionará el período más reciente devuelto por el backend. Si el backend devuelve una lista vacía, se limpiará el período activo y la aplicación mostrará sus estados vacíos; no se conservará un UUID obsoleto.
- **RF-040.** Mientras la recarga posterior a una restauración exitosa esté incompleta, la interfaz bloqueará la visualización y las operaciones sobre datos potencialmente obsoletos. La pantalla Gestión de datos y el control de recuperación permanecerán accesibles.
- **RF-041.** Si falla cualquier consulta de la recarga, se mantendrá el estado de restauración exitosa y se ofrecerá reintentar únicamente la actualización del contexto y de los datos. El reintento no enviará `POST /backups/restore`.
- **RF-042.** Los errores 404 y 409 de restauración provocarán una actualización del catálogo; los errores 422 y 500 se mostrarán según su contrato sin reintentar automáticamente la restauración ni ejecutar una consulta de catálogo innecesaria.
- **RF-043.** La fecha `created_at` se presentará en formato legible en español de Colombia, interpretando el timestamp con zona horaria y mostrando la hora en `America/Bogota`. El valor original no se modificará.
- **RF-044.** El diálogo de restauración gestionará el foco de forma accesible: al abrirlo llevará el foco al contenido/acción segura; mantendrá el foco dentro del diálogo; Escape equivaldrá a cancelar solo antes de iniciar la solicitud; al cerrarse devolverá el foco al control que lo abrió. Durante la solicitud no podrá cerrarse por Escape ni por clic exterior.
- **RF-045.** El estado de recuperación posterior a una restauración será global y persistirá durante la navegación interna hasta que todas las consultas necesarias finalicen correctamente o la usuaria reintente la actualización.

### 4.3 Integración y calidad transversal

- **RF-024.** El cambio de período posterior a restauración deberá actualizar el contexto global y provocar la recarga de los datos de los módulos suscritos.
- **RF-025.** Si el período seleccionado antes de restaurar ya no existe, se seleccionará el último período devuelto por el backend, conforme al contrato.
- **RF-026.** Si el período anterior continúa existiendo, se conservará su selección, pero los datos visibles deberán corresponder al contenido restaurado.
- **RF-027.** Se probará la restauración cuando el período anterior se conserva y cuando deja de existir.
- **RF-028.** Se probará el catálogo vacío, los tres estados de validación, los errores contractuales y la cancelación sin solicitud.
- **RF-029.** La suite de regresión incluirá los flujos principales de FE-001 a FE-006 y las pruebas existentes del backend, sin alterar sus contratos.
- **RF-030.** La pantalla será operable por teclado, tendrá foco visible y mensajes accesibles, conforme a WCAG 2.2 AA.
- **RF-031.** La pantalla funcionará desde 360 px sin desplazamiento horizontal global.
- **RF-032.** Los estados de carga, vacío, error, confirmación y éxito utilizarán los patrones comunes ya validados en el frontend.

## 5. Decisiones aprobadas de refinement

La Product Owner aprobó el 16-11-2026 el conjunto de decisiones FE006-DEC-001 a FE006-DEC-010. Estas decisiones concretan la experiencia de usuario y el comportamiento de integración sin modificar API-001 ni las reglas del backend.

| ID | Tema | Decisión aprobada |
|---|---|---|
| FE006-DEC-001 | Consulta del catálogo | Consultar `GET /backups` al entrar en Gestión de datos y cada vez que se vuelva a entrar. No mantener una caché de visita como fuente de verdad. |
| FE006-DEC-002 | Actualización del catálogo | No incluir botón de actualización ni polling. Si falla la consulta, ofrecer reintento explícito. |
| FE006-DEC-003 | Confirmación y ejecución | Restauración solo para estado listado `valid`; confirmación explícita; cancelación sin request; durante el POST se bloquean cierre, confirmación y solicitudes duplicadas. |
| FE006-DEC-004 | Resultado exitoso | Comunicar HTTP 200 como restauración exitosa y comenzar después la recarga global. Los dos resultados se representan por separado. |
| FE006-DEC-005 | Fallo de recarga | Si falla `GET /periods` o alguna consulta necesaria para refrescar datos, mantener el éxito de restauración, advertir que la actualización quedó incompleta, bloquear temporalmente el uso de datos potencialmente obsoletos y ofrecer reintentar solo la recarga. Nunca repetir el POST de restauración. Esta decisión fue aprobada expresamente por la Product Owner. |
| FE006-DEC-006 | Selección de período | Conservar el UUID seleccionado si aparece en la lista devuelta; si no, seleccionar el período más reciente. Si la lista está vacía, limpiar el período activo y mostrar los estados vacíos correspondientes. |
| FE006-DEC-007 | Recarga de módulos | Después de seleccionar el período, forzar una nueva consulta de los datos de todos los módulos funcionales que dependen del estado persistido, incluso si el UUID activo no cambió. Usar exclusivamente GET existentes y el mecanismo de invalidación/actualización global del frontend. |
| FE006-DEC-008 | Catálogo después de restaurar | No volver a consultar `GET /backups` tras HTTP 200: la restauración no crea ni elimina copias semanales y la copia restaurada ya superó la validación del backend. Ante 404 o 409 sí actualizar el catálogo; ante 422 o 500 no hacer refresco automático del catálogo. |
| FE006-DEC-009 | Formato y accesibilidad | Mostrar `created_at` en español de Colombia y zona horaria `America/Bogota`. El diálogo gestionará foco, teclado y cancelación accesible; no podrá cerrarse cuando el POST esté en curso. |
| FE006-DEC-010 | Validación transversal | Para cerrar FE-006 ejecutar suite frontend completa, suite backend completa, build de producción, integración real con FastAPI, revisión visual responsive desde 360 px y verificación de accesibilidad WCAG 2.2 AA. La validación reproducible con Python 3.14.10 sigue siendo una tarea transversal de Sprint 0, no un requisito que FE-006 deba resolver por sí sola. |

### 5.1 Protocolo obligatorio de recuperación tras restauración

1. Recibir HTTP 200 de `POST /backups/restore`.
2. Registrar y mostrar inmediatamente el resultado de restauración exitosa.
3. Entrar en estado global `refreshing` y evitar que los módulos presenten datos anteriores.
4. Consultar `GET /periods`.
5. Conservar el período activo si continúa disponible; de lo contrario, elegir el de mayor fecha de creación según el orden contractual del endpoint. Si no hay períodos, dejar el contexto sin período activo.
6. Actualizar el contexto global y activar una nueva revisión de datos restaurados.
7. Forzar las consultas GET de los módulos dependientes del estado persistido: Dashboard, alertas, calendario/actividades, presupuesto/gastos e informes, usando el período activo cuando el contrato lo requiera.
8. Solo cuando las consultas necesarias terminen correctamente, retirar el bloqueo de actualización y permitir el uso normal.
9. Si cualquier paso falla, mantener el resultado exitoso de la restauración, mostrar una advertencia de actualización incompleta y mantener bloqueado el acceso a datos que no se han refrescado.
10. La acción «Reintentar actualización» repetirá desde la consulta de períodos y las consultas GET dependientes. No ejecutará de nuevo `POST /backups/restore`.

No se mostrará progreso porcentual porque la API no lo proporciona. La interfaz sí podrá mostrar un estado indeterminado de actualización.

### 5.2 Tratamiento de errores de restauración

| Respuesta | Comportamiento |
|---|---|
| 404 `BACKUP_NOT_FOUND` | Informar que la copia ya no está disponible; volver a consultar el catálogo. No repetir el POST. |
| 409 `BACKUP_NOT_RESTORABLE` | Informar que la copia no superó la validación actual; volver a consultar el catálogo para mostrar el nuevo estado. No repetir el POST. |
| 422 `RESTORE_CONFIRMATION_REQUIRED` | Informar que la solicitud no fue aceptada; conservar el catálogo actual y no reintentar automáticamente. |
| 500 `BACKUP_RESTORE_FAILED` | Informar que el backend no pudo completar la restauración y conservó los datos anteriores según el contrato; no reintentar ni refrescar automáticamente el catálogo. La usuaria podrá iniciar una nueva operación manual desde el catálogo tras una nueva confirmación, si lo desea. |

No quedan preguntas de Product Owner pendientes para FE-006. Cualquier descubrimiento que implique cambiar un contrato aprobado deberá detenerse y proponerse como cambio formal, no resolverse unilateralmente en frontend.

## 6. Criterios de aceptación preliminares

- **CA-001.** El catálogo consulta únicamente `GET /backups` y presenta como máximo las 15 copias semanales en el orden del backend.
- **CA-002.** Cada fila muestra fecha, identificador y estado de validación.
- **CA-003.** Las copias `invalid` y `not_validated` no permiten iniciar restauración.
- **CA-004.** El estado vacío no ofrece acciones de restauración.
- **CA-005.** La carga y el error de catálogo tienen presentación diferenciada y el error permite reintentar.
- **CA-006.** Cancelar el diálogo no envía `POST /backups/restore`.
- **CA-007.** Confirmar envía exactamente `backup_id` y `confirmed: true`.
- **CA-008.** No se permiten envíos duplicados durante la restauración.
- **CA-009.** El éxito se anuncia únicamente tras recibir HTTP 200.
- **CA-010.** Los errores contractuales no se presentan como restauraciones exitosas.
- **CA-011.** Tras el éxito se recargan períodos y datos; se conserva el período activo si existe y, de lo contrario, se selecciona el último creado.
- **CA-012.** Los datos visibles corresponden al contenido restaurado incluso cuando el identificador del período activo no cambia.
- **CA-013.** No se exponen rutas, referencias internas, archivos JSON ni respaldos `pre_write`.
- **CA-014.** La pantalla cumple responsive desde 360 px y los criterios de accesibilidad aplicables.
- **CA-015.** La regresión no introduce fallos en FE-001 a FE-005 ni en los contratos backend.
- **CA-016.** Al entrar y volver a entrar en Gestión de datos se ejecuta una nueva consulta de catálogo; no existe polling ni botón de actualización.
- **CA-017.** Tras HTTP 200 de restauración se comunica éxito y se inicia una recarga global independiente; un fallo de recarga no revierte ni oculta el éxito.
- **CA-018.** La recarga conserva el período activo si existe; si no, selecciona el período más reciente; si no hay períodos, limpia la selección.
- **CA-019.** Los datos de todos los módulos dependientes se vuelven a consultar aunque el UUID del período activo permanezca igual.
- **CA-020.** Mientras la recarga esté incompleta no se muestran ni permiten modificar datos potencialmente obsoletos.
- **CA-021.** Reintentar la recarga ejecuta únicamente GET de períodos y módulos; no ejecuta `POST /backups/restore`.
- **CA-022.** Tras 404 o 409 se actualiza el catálogo; tras 422 o 500 no se ejecuta un refresco automático del catálogo.
- **CA-023.** La fecha del catálogo se muestra en español de Colombia y zona horaria `America/Bogota`.
- **CA-024.** El diálogo de restauración cumple gestión de foco y teclado; no se puede cerrar mientras la restauración esté en curso.
- **CA-025.** La regresión integral cubre FE-001 a FE-006, suite backend, integración FastAPI, build, responsive y WCAG 2.2 AA.

## 7. Estrategia de pruebas preliminar

### 7.1 Servicio API

- Consulta del catálogo y validación de la ruta sin parámetros.
- Preservación de los campos y estados recibidos.
- Envío del request exacto de restauración.
- Tratamiento de respuestas exitosas y errores contractuales.
- Prevención de solicitudes duplicadas.

### 7.2 Componentes

- Estados loading, empty, error y contenido.
- Renderizado de los tres estados de validación.
- Habilitación y deshabilitación de restauración.
- Confirmación, cancelación, carga y resultado.
- Mensajes accesibles y foco del diálogo.

### 7.3 Integración

- Catálogo real con FastAPI.
- Restauración confirmada y cancelada.
- Copia inválida o no restaurable.
- Errores 404, 409, 422 y 500.
- Conservación del período seleccionado.
- Selección del último período cuando el anterior desaparece.
- Recarga efectiva de datos después de restaurar, incluso si el ID del período no cambia.
- Fallo de `GET /periods` posterior a HTTP 200 de restauración: éxito preservado, bloqueo de datos obsoletos y reintento GET-only.
- Fallo de cada consulta de módulo durante la recarga global y recuperación sin POST de restauración.
- Restauración con período activo conservado, sustituido por el más reciente y catálogo de períodos vacío.
- Respuestas 404/409 con actualización del catálogo; 422/500 sin actualización automática.

### 7.4 Regresión y calidad

- Suite frontend completa FE-001 a FE-006.
- Suite backend completa.
- Build de producción.
- Integración real con FastAPI.
- Revisión visual en escritorio y móvil desde 360 px.
- Navegación por teclado, foco visible y mensajes accesibles.
- Sin regresiones en informes, presupuesto/gastos, actividades, calendario, alertas ni Dashboard.

## 8. Definition of Done preliminar

FE-006 podrá cerrarse cuando:

1. La especificación FE-006 esté aprobada y sus decisiones abiertas estén resueltas.
2. Los requisitos y criterios de aceptación aprobados estén implementados.
3. Se consuman exclusivamente los contratos de API-001 §5.9.
4. No se expongan archivos, rutas ni metadatos internos.
5. La restauración requiera confirmación explícita y respete API-DEC-038.
6. La recarga del contexto y de todos los módulos esté probada tanto si el período activo se conserva como si cambia o no existen períodos.
7. Los fallos de recarga posterior a restauración se recuperen mediante consultas GET sin repetir el POST destructivo.
8. Las pruebas unitarias, de componentes, integración y regresión estén aprobadas.
9. La suite backend completa y la suite frontend completa pasen sin fallos.
10. El build de producción sea satisfactorio.
11. Se confirme integración real con FastAPI.
12. Se verifiquen responsive desde 360 px, accesibilidad WCAG 2.2 AA y navegación por teclado.
13. Los cambios estén publicados en GitHub en `feat/backend-domain-foundation`.
14. La usuaria sincronice localmente y comparta evidencia satisfactoria.
15. El estado del proyecto y el roadmap se actualicen después de recibir esa evidencia.
