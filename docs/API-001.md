# API-001 — Contratos de endpoints REST

**Proyecto:** Sistema de Planificación y Control de Vacaciones Decembrinas  
**Versión:** 0.3  
**Estado:** APROBADA  
**Tipo:** Especificación técnica de API  
**Arquitectura relacionada:** ARCH-001  
**Modelo de datos relacionado:** DATA-001  
**Especificaciones funcionales relacionadas:** SPEC-001 a SPEC-006

---

## 1. Objetivo

Definir los contratos de comunicación entre el frontend React y el backend FastAPI, estableciendo endpoints, métodos HTTP, parámetros, estructuras de solicitud y respuesta, códigos de estado, validaciones y tratamiento de errores.

Este documento constituye la referencia contractual para implementar los controladores de API y su integración con los servicios del backend.

## 2. Alcance

La API cubrirá los siguientes módulos:

1. Períodos.
2. Actividades.
3. Calendario.
4. Alertas.
5. Presupuestos.
6. Gastos e historial de modificaciones.
7. Dashboard.
8. Informes y comparación histórica.
9. Copias de seguridad y restauración.

No contempla autenticación, servicios externos, integraciones con calendarios externos ni persistencia desde el frontend.

## 3. Convenciones generales

### 3.1 Configuración

| Elemento | Convención |
|---|---|
| Base URL | `/api/v1` |
| Protocolo | HTTP local |
| Host | `localhost` exclusivamente |
| Formato de intercambio | JSON |
| Content-Type | `application/json` |
| Identificadores | UUID |
| Fechas | `YYYY-MM-DD` |
| Horas | `HH:MM` |
| Timestamps | ISO 8601 con zona horaria |
| Zona horaria | `America/Bogota` |
| Moneda | COP |
| Importes JSON | Cadenas decimales |
| Importes backend | Decimal |

### 3.2 Métodos HTTP

| Método | Uso |
|---|---|
| GET | Consultar recursos |
| POST | Crear recursos o ejecutar operaciones |
| PUT | Reemplazar o actualizar completamente un recurso |
| PATCH | Modificar parcialmente un recurso |
| DELETE | Eliminar un recurso |

### 3.3 Estructura de respuestas exitosas

Todas las respuestas exitosas que contengan información utilizarán una propiedad `data`.

Ejemplo:

```json
{
  "data": {
    "id": "UUID",
    "name": "Vacaciones decembrinas 2026"
  }
}
```

Las respuestas de listados podrán incluir `meta` cuando corresponda:

```json
{
  "data": [],
  "meta": {
    "total": 0,
    "page": 1,
    "page_size": 50,
    "total_pages": 0
  }
}
```

Las operaciones que respondan HTTP 204 no incluirán cuerpo.

### 3.4 Paginación

La paginación será opcional.

Parámetros:

- `page`: número de página.
- `page_size`: cantidad de registros por página.

Cuando se soliciten ambos parámetros, el backend devolverá los registros correspondientes y los metadatos de paginación.

Cuando no se solicite paginación, se devolverá el conjunto completo de resultados que cumpla los filtros.

La paginación no modificará los datos ni los criterios de filtrado.

### 3.5 Filtros

Los filtros se transmitirán mediante parámetros de consulta en los endpoints de listado.

Ejemplo:

```http
GET /api/v1/activities?period_id=UUID&category=Viajes&status=Pendiente
```

Los filtros serán combinables cuando la especificación del módulo lo permita.

El backend validará los valores y aplicará los filtros antes de devolver los resultados.

### 3.6 Actualizaciones

Se utilizará:

- `PUT` cuando se envíe el conjunto completo de campos editables.
- `PATCH` cuando se modifiquen únicamente determinados campos.

La disponibilidad de cada método dependerá del recurso y de sus reglas de negocio.

## 4. Formato de errores

Todas las respuestas de error utilizarán la siguiente estructura:

```json
{
  "error": {
    "code": "ACTIVITY_NOT_FOUND",
    "message": "No se encontró la actividad solicitada.",
    "details": []
  }
}
```

Campos:

| Campo | Descripción |
|---|---|
| `code` | Código estable para identificar el error |
| `message` | Mensaje comprensible para el usuario |
| `details` | Información adicional sobre los errores o validaciones |

Los detalles técnicos internos no se expondrán al frontend. Se conservarán en los registros locales según SPEC-006.

### 4.1 Códigos HTTP

| Código | Aplicación |
|---|---|
| 200 | Consulta o actualización exitosa |
| 201 | Recurso creado |
| 204 | Eliminación exitosa sin contenido |
| 400 | Solicitud incorrecta |
| 404 | Recurso inexistente |
| 409 | Conflicto con una regla de negocio |
| 422 | Datos inválidos o errores de validación |
| 500 | Error interno del servidor |

Las validaciones de datos utilizarán 422. Los conflictos con reglas de negocio utilizarán 409.

## 5. Contratos por módulo

### 5.1 Períodos

Un período representa un ciclo de planificación de vacaciones decembrinas. Su año se determina exclusivamente a partir del año calendario de `start_date`.

#### Endpoints

| Método | Endpoint | Descripción |
|---|---|---|
| GET | `/periods` | Consultar períodos |
| POST | `/periods` | Crear período |
| GET | `/periods/{period_id}` | Consultar un período |
| PUT | `/periods/{period_id}` | Actualizar completamente un período |

No existe endpoint DELETE: la eliminación de períodos está prohibida.

#### Consultar períodos

`GET /periods`

Parámetros opcionales:

- `page`: número de página.
- `page_size`: cantidad de registros por página.

La paginación se aplica únicamente cuando se envían ambos parámetros. Sin ellos, se devuelve el conjunto completo. La respuesta contiene `data` como arreglo de períodos y, cuando se usa paginación, `meta` con `total`, `page`, `page_size` y `total_pages`.

#### Crear período

`POST /periods`

Request:

```json
{
  "name": "Vacaciones decembrinas 2026",
  "start_date": "2026-12-20",
  "end_date": "2027-01-10"
}
```

El cliente no enviará `id`, `year` ni `created_at`. El backend generará el UUID y el timestamp, y calculará `year` a partir del año de `start_date`.

Response: HTTP 201.

```json
{
  "data": {
    "id": "UUID",
    "year": 2026,
    "name": "Vacaciones decembrinas 2026",
    "start_date": "2026-12-20",
    "end_date": "2027-01-10",
    "created_at": "2026-11-14T10:00:00-05:00"
  }
}
```

#### Consultar un período

`GET /periods/{period_id}`

Devuelve HTTP 200 con el período dentro de `data`. Si el UUID no corresponde a un período existente, devuelve HTTP 404.

#### Actualizar período

`PUT /periods/{period_id}`

PUT requiere el conjunto completo de campos editables:

```json
{
  "name": "Vacaciones familiares 2026",
  "start_date": "2026-12-20",
  "end_date": "2027-01-10"
}
```

El cliente no enviará `id`, `year` ni `created_at`. El backend recalculará `year` desde `start_date` y conservará el identificador y la fecha de creación.

#### Validaciones y conflictos

- `name` es obligatorio y lo proporciona el usuario.
- `start_date` y `end_date` son obligatorias y deben ser fechas válidas.
- `start_date` debe ser anterior o igual a `end_date`.
- Se permiten períodos que atraviesen dos años calendario.
- `year` corresponde siempre al año calendario de `start_date`; no es un campo de entrada ni editable directamente.
- Solo puede existir un período por año. La unicidad se determina por el año derivado de `start_date`.
- Al actualizar, el backend comprobará que ninguna actividad existente quede fuera del nuevo rango. Si alguna quedaría fuera, rechazará la operación sin modificar el período.
- No se permite eliminar períodos.

Errores relevantes: HTTP 404 si el período no existe; HTTP 409 si el año ya está ocupado o el nuevo rango excluye actividades existentes; HTTP 422 si faltan campos o las fechas no son válidas.

### 5.2 Actividades

Una actividad pertenece a un único período y mantiene esa relación durante toda su existencia.

#### Endpoints

| Método | Endpoint | Descripción |
|---|---|---|
| GET | `/activities` | Consultar actividades |
| POST | `/activities` | Crear actividad |
| GET | `/activities/{activity_id}` | Consultar actividad |
| PUT | `/activities/{activity_id}` | Actualizar todos los campos editables |
| PATCH | `/activities/{activity_id}` | Actualizar parcialmente campos editables |
| DELETE | `/activities/{activity_id}` | Eliminar actividad y sus dependencias |

#### Crear actividad

`POST /activities`

Request:

```json
{
  "period_id": "UUID",
  "name": "Viaje familiar",
  "description": "Viaje de vacaciones",
  "category": "Viajes",
  "destination": "Santa Marta",
  "start_date": "2026-12-22",
  "end_date": "2026-12-27",
  "start_time": "08:00",
  "end_time": "18:00",
  "priority": "Alta"
}
```

El request no admite `id`, `status`, `created_at` ni `updated_at`. Si el cliente envía `status` en la creación, la solicitud se rechazará con HTTP 422; el backend asigna automáticamente `status = "Pendiente"`. El backend genera el UUID y los timestamps.

Response: HTTP 201.

```json
{
  "data": {
    "id": "UUID",
    "period_id": "UUID",
    "name": "Viaje familiar",
    "description": "Viaje de vacaciones",
    "category": "Viajes",
    "destination": "Santa Marta",
    "start_date": "2026-12-22",
    "end_date": "2026-12-27",
    "start_time": "08:00",
    "end_time": "18:00",
    "priority": "Alta",
    "status": "Pendiente",
    "created_at": "2026-11-14T10:00:00-05:00",
    "updated_at": "2026-11-14T10:00:00-05:00"
  }
}
```

#### Consultar actividades

`GET /activities`

Filtros opcionales y combinables:

- `period_id`: UUID del período.
- `category`: categoría permitida.
- `priority`: Alta, Media o Baja.
- `status`: Pendiente, En progreso, Completada o Cancelada.
- `start_date`: fecha de inicio para acotar la consulta.
- `end_date`: fecha de finalización para acotar la consulta.
- `destination`: destino.

También admite `page` y `page_size` como parámetros opcionales de paginación. Se aplican los filtros antes de paginar. Si ambos parámetros están presentes, la respuesta incluye `meta`; si no se envían, devuelve todos los resultados coincidentes.

Response HTTP 200:

```json
{
  "data": [
    {
      "id": "UUID",
      "period_id": "UUID",
      "name": "Viaje familiar",
      "description": "Viaje de vacaciones",
      "category": "Viajes",
      "destination": "Santa Marta",
      "start_date": "2026-12-22",
      "end_date": "2026-12-27",
      "start_time": "08:00",
      "end_time": "18:00",
      "priority": "Alta",
      "status": "Pendiente",
      "created_at": "2026-11-14T10:00:00-05:00",
      "updated_at": "2026-11-14T10:00:00-05:00"
    }
  ]
}
```

#### Consultar una actividad

`GET /activities/{activity_id}`

Devuelve HTTP 200 con la actividad dentro de `data`. Si no existe, devuelve HTTP 404.

#### Actualización

- PUT recibe todos los campos editables de la actividad.
- PATCH recibe únicamente los campos que se desean modificar.
- Los campos editables son `name`, `description`, `category`, `destination`, `start_date`, `end_date`, `start_time`, `end_time`, `priority` y `status`.
- `period_id` es inmutable después de crear la actividad. No forma parte de los campos editables. Si se incluye en PUT o PATCH con intención de modificarlo, la solicitud se rechazará; no existe operación para trasladar una actividad a otro período.
- `id`, `created_at` y `updated_at` son administrados por el backend. `updated_at` se actualiza cuando una modificación es aceptada.
- La modificación de `status` debe respetar exclusivamente las transiciones aprobadas: Pendiente → En progreso; En progreso → Completada; y Cancelada desde cualquiera de los estados. No se permiten transiciones de regreso ni reapertura.
- La transición no válida se rechaza con HTTP 409 y no modifica el registro.

#### Eliminación

`DELETE /activities/{activity_id}`

Response: HTTP 204 sin cuerpo.

La eliminación es definitiva y debe ejecutarse como una única operación consistente. El backend eliminará:

- La actividad.
- Todos los gastos asociados a la actividad.
- Todo el historial de modificaciones de esos gastos.
- Todas las alertas asociadas a la actividad.
- El historial de eventos contenido en esas alertas.

No se conservarán registros huérfanos. Si la operación no puede completarse íntegramente, no se aceptará una eliminación parcial.

#### Validaciones de fechas, horarios y solapamientos

- `period_id` debe identificar un período existente.
- Las fechas de la actividad deben permanecer dentro del rango inclusivo del período.
- `start_date` y `end_date` son obligatorias y deben ser fechas válidas; `start_date` no puede ser posterior a `end_date`.
- `start_time` y `end_time` son obligatorias y deben tener formato `HH:MM`.
- Las fechas y horas son explícitas: el backend no incrementará ni corregirá automáticamente `end_date`.
- Para una actividad que cruza medianoche, `end_date` debe contener la fecha real del día siguiente o posterior. Por ejemplo, de 22:00 a 02:00 se envían fechas explícitas en días consecutivos.
- Si `start_date` y `end_date` son iguales, `end_time` debe ser posterior a `start_time`. Si es igual o anterior, la solicitud se rechaza con HTTP 422.
- La duración temporal se construye combinando cada fecha con su hora correspondiente. La validación de solapamientos considera el intervalo completo, incluso para actividades multidiarias.
- Los intervalos son semiabiertos `[inicio, finalización)`: incluyen el instante inicial y excluyen el instante final. Por tanto, una actividad puede comenzar exactamente cuando termina otra.
- No se permiten solapamientos entre actividades del mismo período. Para dos intervalos A y B, existe solapamiento cuando `A.inicio < B.fin` y `B.inicio < A.fin`. Al actualizar, la actividad actual se excluye de la comparación consigo misma.
- `category` debe pertenecer al catálogo: Viajes, Transporte, Alojamiento, Recreación, Turismo, Reuniones familiares u Otros.
- `priority` debe ser Alta, Media o Baja.
- Los estados permitidos son Pendiente, En progreso, Completada y Cancelada.

#### Errores relevantes

| Situación | HTTP |
|---|---:|
| Actividad inexistente | 404 |
| Período inexistente | 404 |
| Fechas u horas con formato o combinación inválida | 422 |
| Campo obligatorio ausente o valor fuera de catálogo | 422 |
| Se envía `status` al crear una actividad | 422 |
| Se intenta cambiar `period_id` | 422 |
| Actividad fuera del período | 409 |
| Solapamiento con otra actividad del mismo período | 409 |
| Transición de estado no permitida | 409 |
| Eliminación que no puede completarse íntegramente | 500 |

### 5.3 Calendario

#### Endpoint

`GET /calendar`

Devuelve las actividades del período y rango solicitados, aplicando los filtros indicados. Cada actividad conserva su identificador único aunque se represente visualmente en varios días.

#### Parámetros

| Parámetro | Tipo | Obligatorio | Regla |
|---|---|---:|---|
| `period_id` | UUID | Sí | Período consultado. |
| `start_date` | Date | Sí | Primer día del rango, inclusivo. |
| `end_date` | Date | Sí | Último día del rango, inclusivo. |
| `category` | Enum | No | Categoría permitida. |
| `priority` | Enum | No | Alta, Media o Baja. |
| `status` | Enum | No | Pendiente, En progreso, Completada o Cancelada. |

Los filtros son combinables. No se admite paginación en este endpoint: la consulta representa el rango visible del calendario.

#### Reglas de consulta

- El período debe existir; de lo contrario, HTTP 404.
- Las fechas deben ser válidas y `start_date` debe ser anterior o igual a `end_date`; en caso contrario, HTTP 422.
- El rango solicitado incluye ambos extremos.
- Se incluye una actividad cuando su intervalo de fechas intersecta el rango: `activity.start_date <= end_date` y `activity.end_date >= start_date`.
- Las actividades multidiarias que intersecten el rango se devuelven una sola vez, con sus fechas y horas originales completas. La representación en cada día corresponde al frontend.
- Solo se devuelven actividades del período solicitado.
- Las actividades Canceladas se incluyen cuando no se filtra por estado, de acuerdo con UI-001.
- El backend calcula la información derivada necesaria, incluido el indicador de vencimiento, sin persistir valores derivados.

#### Response HTTP 200

```json
{
  "data": [
    {
      "id": "UUID",
      "period_id": "UUID",
      "name": "Viaje familiar",
      "description": "Viaje de vacaciones",
      "category": "Viajes",
      "destination": "Santa Marta",
      "start_date": "2026-12-22",
      "end_date": "2026-12-27",
      "start_time": "08:00",
      "end_time": "18:00",
      "priority": "Alta",
      "status": "Pendiente",
      "is_overdue": false
    }
  ]
}
```

`is_overdue` es calculado por el backend conforme a SPEC-002 y no se persiste. Los demás campos respetan DATA-001 y SPEC-002.

#### Errores relevantes

| Situación | HTTP |
|---|---:|
| Período inexistente | 404 |
| Falta un parámetro obligatorio | 422 |
| UUID, fechas, rango o filtro inválido | 422 |

### 5.4 Alertas

#### Endpoints

| Método | Endpoint | Descripción |
|---|---|---|
| GET | `/alerts` | Consultar alertas |
| POST | `/alerts/evaluate` | Evaluar condiciones de alertas |
| PATCH | `/alerts/{alert_id}/review` | Marcar alerta como revisada |

Las alertas respetan los tipos, estados, historial, condiciones y reglas de ciclo de vida establecidos en SPEC-003 y DATA-001. Existe como máximo una alerta por combinación de actividad y tipo (DEC-024).

#### Estructura de alerta

Cada alerta se devuelve con sus campos persistidos y el resumen de actividad necesario para identificarla. El historial se incluye embebido en `history`.

```json
{
  "id": "UUID",
  "activity_id": "UUID",
  "type": "Próxima",
  "status": "Pendiente",
  "condition_active": true,
  "created_at": "2026-12-21T08:00:00-05:00",
  "updated_at": "2026-12-21T08:00:00-05:00",
  "reviewed_at": null,
  "activity": {
    "id": "UUID",
    "name": "Viaje familiar",
    "start_date": "2026-12-22",
    "end_date": "2026-12-27",
    "start_time": "08:00",
    "end_time": "18:00",
    "priority": "Alta",
    "status": "Pendiente"
  },
  "history": [
    {
      "event_type": "created",
      "occurred_at": "2026-12-21T08:00:00-05:00"
    }
  ]
}
```

Los valores de `type`, `status` y `history.event_type` corresponden exactamente a DATA-001. `activity` es una proyección de lectura, no una entidad modificable desde este endpoint.

#### Consultar alertas

`GET /alerts`

Parámetros opcionales y combinables:

| Parámetro | Tipo | Regla |
|---|---|---|
| `period_id` | UUID | Período de la actividad relacionada. |
| `activity_id` | UUID | Actividad relacionada. |
| `type` | Enum | Próxima, Vencida o Prioridad alta. |
| `status` | Enum | Pendiente o Revisada. |
| `condition_active` | Boolean | Condición vigente o inactiva. |
| `page` | Integer | Página solicitada. |
| `page_size` | Integer | Cantidad por página. |

Por defecto, la consulta incluye alertas activas e inactivas. Para consultar solo alertas vigentes se enviará `condition_active=true`; para consultar solo registros inactivos, `condition_active=false`. `status` y `condition_active` son filtros independientes: una alerta puede estar Revisada y tener su condición activa o inactiva.

La respuesta contiene `data` como arreglo de alertas, incluyendo `activity` y `history`. Cuando se envían ambos parámetros de paginación, también incluye `meta` con `total`, `page`, `page_size` y `total_pages`. Los filtros se aplican antes de paginar.

Si se envía `period_id` o `activity_id` y el identificador no existe, se devuelve HTTP 404. Los UUID, enumeraciones, booleanos y parámetros de paginación inválidos producen HTTP 422.

#### Evaluar alertas

`POST /alerts/evaluate`

Request:

```json
{
  "period_id": "UUID"
}
```

`period_id` es obligatorio. La evaluación se limita exclusivamente al período seleccionado en la aplicación. El backend comprobará que el período exista.

La operación se ejecutará al abrir la aplicación para el período seleccionado. También se ejecutará desde los servicios del backend cuando una modificación de actividad afecte las condiciones de sus alertas, respetando SPEC-003. Esta reevaluación por cambios no requiere una llamada adicional del frontend.

Reglas de evaluación:

- **Próxima:** la condición se cumple cuando faltan 24 horas o menos para el inicio y el instante de inicio todavía no ha llegado. El cálculo combina `start_date` y `start_time` en la zona horaria `America/Bogota`. No se genera para actividades Completadas o Canceladas.
- **Vencida:** para actividades de un día, la condición se cumple al finalizar la fecha programada; para actividades multidiarias, al finalizar la fecha de finalización. Solo aplica a actividades Pendientes o En progreso. Completadas y Canceladas nunca se consideran vencidas.
- **Prioridad alta:** la condición se cumple desde que se registra una actividad con prioridad Alta y se mantiene mientras la actividad sea Pendiente o En progreso. No aplica a actividades Completadas o Canceladas.
- Cuando una condición aparece por primera vez, se crea la alerta correspondiente.
- Cuando desaparece, se actualiza `condition_active=false` y se registra el evento correspondiente; no se elimina la alerta ni su historial.
- Si vuelve a cumplirse, se recupera la alerta existente, sin duplicados. Si su estado era Revisada, conserva ese estado conforme a DEC-027.
- Existe una alerta por actividad/tipo como máximo. Una evaluación repetida con los mismos datos no crea eventos duplicados ni altera innecesariamente los registros.
- La evaluación no modifica el estado de las actividades.

Response HTTP 200:

```json
{
  "data": {
    "period_id": "UUID",
    "evaluated_at": "2026-12-21T08:00:00-05:00",
    "created_count": 1,
    "activated_count": 0,
    "deactivated_count": 0,
    "reactivated_count": 0,
    "active_count": 3
  }
}
```

Los contadores describen los cambios realizados durante la evaluación. `active_count` corresponde al total de alertas con `condition_active=true` del período evaluado, sin importar si su estado es Pendiente o Revisada.

Errores relevantes: HTTP 404 si el período no existe; HTTP 422 si falta `period_id` o su formato es inválido; HTTP 500 ante un error interno no recuperable. La operación preservará la integridad de los registros y sus historiales.

#### Marcar alerta como revisada

`PATCH /alerts/{alert_id}/review`

No requiere cuerpo. La operación cambia `status` a `Revisada`, establece `reviewed_at` con el timestamp actual y agrega el evento `reviewed` al historial. No modifica `condition_active`, la condición de negocio ni el estado de la actividad.

La operación es idempotente: si la alerta ya está Revisada, devuelve su representación actual sin agregar otro evento `reviewed` ni cambiar `reviewed_at`.

Response HTTP 200:

```json
{
  "data": {
    "id": "UUID",
    "activity_id": "UUID",
    "type": "Próxima",
    "status": "Revisada",
    "condition_active": true,
    "reviewed_at": "2026-12-21T08:15:00-05:00",
    "activity": {
      "id": "UUID",
      "name": "Viaje familiar",
      "start_date": "2026-12-22",
      "end_date": "2026-12-27",
      "start_time": "08:00",
```

### 5.5 Presupuestos

Cada período podrá tener un presupuesto general y asignaciones por categoría.

| POST | `/periods/{period_id}/budget` | Crear presupuesto |

#### Crear presupuesto

`POST /periods/{period_id}/budget`

Request:

```json
{
  "total_budget": "5000000.00",
  "category_budgets": [
    {
      "category": "Viajes",
      "amount": "2500000.00"
    },
    {

      "amount": "1500000.00"
    },
    {
      "category": "Recreación",
      "amount": "1000000.00"
    }
  ]
}
```

#### Actualizar presupuesto

`PUT /periods/{period_id}/budget`

Recibirá el presupuesto general y todas las asignaciones por categoría.

**Validaciones:**

- Debe existir el período.
- Solo puede existir un presupuesto por período.
- Los importes serán decimales válidos con hasta dos posiciones.
- La suma de las asignaciones no podrá superar el presupuesto general.
- Los gastos podrán superar los presupuestos; se generarán advertencias, no bloqueos.
- Si se reduce el presupuesto general por debajo de las asignaciones existentes, será necesario ajustar las categorías antes de guardar.
- Las modificaciones conservarán la coherencia financiera.

Los indicadores derivados se calcularán en el backend.

### 5.9 Copias de seguridad y restauración

#### Endpoints

| Método | Endpoint | Descripción |
|---|---|---|
| GET | `/backups` | Consultar copias disponibles |
| POST | `/backups/restore` | Restaurar una copia |

La generación semanal y los respaldos previos a escrituras serán responsabilidad del servicio de persistencia y backups, según SPEC-006 y ARCH-001.

No se expondrá al frontend la ruta física de los archivos.

#### Consultar copias

`GET /backups`

Devolverá información descriptiva de las copias disponibles, su fecha y su validez.

#### Restaurar copia

`POST /backups/restore`

Request:

```json
{
  "backup_id": "UUID",
  "confirmed": true
}
```

El backend deberá:

1. Verificar que la copia exista.
2. Validar su integridad y estructura.
3. Solicitar confirmación explícita mediante el contrato.
4. Conservar los datos actuales antes de restaurar, según los mecanismos de protección establecidos.
5. Restaurar la última copia válida seleccionada.
6. Informar el resultado de la operación.

Si la copia no es válida, no se reemplazarán los datos actuales.

La operación no permitirá restauraciones silenciosas ni automáticas desde el frontend.

## 6. Reglas transversales de negocio

Todos los endpoints deberán respetar las reglas aprobadas en las especificaciones funcionales.

### 6.1 Integridad

- Los UUID serán generados y validados por el backend.
- Las relaciones entre entidades deberán existir y ser válidas.
- No se permitirán registros huérfanos.
- Las operaciones que involucren múltiples entidades deberán conservar la integridad del conjunto JSON.

### 6.2 Persistencia

- El frontend nunca escribirá directamente en `datos_vacaciones.json`.
- Todas las modificaciones pasarán por servicios del backend.
- Las escrituras utilizarán el mecanismo atómico definido en ARCH-001 y SPEC-006.
- El control de concurrencia será responsabilidad del backend.

### 6.3 Cálculos

Los importes se procesarán mediante Decimal.

El backend calculará:

- Gastos totales.
- Saldos.
- Ejecución presupuestaria.
- Cumplimiento de actividades.
- Conteos por estado.
- Actividades vencidas.
- Indicadores de dashboard e informes.

No se persistirán valores derivados definidos como calculables en DATA-001.

### 6.4 Alertas

- Las alertas se evaluarán al abrir la aplicación para el período seleccionado y cuando las modificaciones de actividades afecten sus condiciones, respetando SPEC-003.
- `POST /alerts/evaluate` requiere el `period_id` seleccionado y no procesa otros períodos.
- Las alertas próximas se activan dentro de las 24 horas previas al inicio, siempre que la actividad no haya comenzado.
- Se mantiene una alerta por actividad y tipo. La desactivación conserva el registro y su historial; la reactivación recupera el registro existente.
- La reactivación conserva el estado Revisada cuando corresponda, según DEC-027.
- El estado (`Pendiente`/`Revisada`) y la vigencia de la condición (`condition_active`) son dimensiones independientes.
- La consulta ordinaria incluye registros activos e inactivos y embebe el historial en cada alerta.
- Marcar como revisada no modifica la actividad. Repetir la operación no crea eventos de historial duplicados.
- No se ejecutarán procesos permanentes en segundo plano ni servicios externos de notificación.
- Eliminar una actividad elimina sus alertas e historiales asociados, de forma íntegra.

### 6.5 Seguridad y privacidad

- No se implementará autenticación.
- El servidor escuchará exclusivamente en localhost.
- No se transmitirán datos a servicios externos.
- Los errores técnicos se registrarán localmente.

## 7. Relación entre API, servicios y persistencia

La API no implementará directamente las reglas de negocio ni accederá directamente al archivo JSON.

El flujo será:

```text
Frontend React
      ↓
Endpoints FastAPI
      ↓
Servicios de dominio
      ↓
Repositorios JSON
      ↓
datos_vacaciones.json
```

Los controladores validarán la estructura de entrada mediante Pydantic y delegarán las operaciones a los servicios correspondientes.

Los servicios aplicarán las reglas funcionales y solicitarán las operaciones de persistencia necesarias.

## 8. Criterios de aceptación

API-001 se considerará implementable cuando se cumpla lo siguiente:

1. Todos los módulos funcionales cuentan con endpoints definidos.
2. Cada endpoint tiene método HTTP, ruta y propósito documentados.
3. Los contratos de entrada y salida respetan DATA-001 y las reglas funcionales aprobadas.
4. Las respuestas exitosas con contenido utilizan la estructura `data`, excepto las descargas y las respuestas sin contenido.
5. Los errores siguen la estructura uniforme `{error:{code,message,details}}`.
6. Los filtros admitidos están documentados y se pueden combinar cuando corresponda.
7. La paginación es opcional y utiliza `page` y `page_size`.
8. PUT y PATCH tienen responsabilidades diferenciadas.
9. Los códigos HTTP aprobados están definidos y se aplican coherentemente.
10. Las operaciones de eliminación respetan las reglas de integridad y no dejan registros huérfanos.
11. Los cálculos financieros y de actividades se realizan en backend.
12. Los informes permiten exportación PDF y Excel.
13. La restauración requiere confirmación y validación de la copia.
14. La API respeta la arquitectura por capas.
15. La documentación OpenAPI refleja los contratos implementados.
16. No existen endpoints que permitan al frontend manipular directamente el archivo JSON.
17. La creación de períodos no recibe `year`; el backend lo deriva de `start_date`, exige `name` y garantiza un período por año.
18. La actualización de períodos rechaza cambios que dejen actividades fuera del nuevo rango.
19. La creación de actividades no recibe `status`; el backend asigna `Pendiente` y genera UUID y timestamps.
20. `period_id` de una actividad no puede cambiar después de su creación.
21. Las actividades que cruzan medianoche utilizan fechas explícitas y el backend no corrige fechas automáticamente.
22. La validación temporal usa intervalos `[inicio, finalización)`, considera actividades multidiarias y permite el inicio exacto al finalizar otra.
23. Las transiciones de estado respetan DEC-017, sin transiciones de regreso ni reapertura.
24. Eliminar una actividad elimina también, de forma íntegra, gastos, historiales de gastos, alertas e historiales de alertas asociados.
25. El calendario exige período y rango de fechas válidos, interpreta ambos extremos como inclusivos y aplica filtros combinables.
26. La consulta del calendario incluye actividades cuyo rango de fechas intersecta el rango solicitado; cada actividad multidiaria aparece una sola vez en la respuesta.
27. El calendario incluye actividades Canceladas por defecto y calcula la condición de vencimiento en backend.
28. La evaluación de alertas requiere un período existente y solo evalúa actividades de ese período.
29. La alerta Próxima se activa dentro de las 24 horas previas al inicio y nunca después de que la actividad haya comenzado; no aplica a actividades Completadas o Canceladas.
30. La consulta normal de alertas incluye registros activos e inactivos, permite filtrar por `condition_active` y devuelve el historial embebido.
31. La evaluación respeta los tipos, estados, desactivación, reactivación, ausencia de duplicados y conservación del estado Revisada establecidos en SPEC-003, DATA-001 y DEC-027.
32. Marcar una alerta como revisada no modifica la actividad y repetir la operación no duplica el evento de historial ni altera `reviewed_at`.

## Observaciones técnicas registradas en la fuente

Hay tres aspectos técnicos que conviene revisar especialmente porque afectan la implementación:

1. **Evaluación de alertas:** el frontend llamará a `POST /alerts/evaluate` al iniciar la aplicación. Las modificaciones de actividades también podrán provocar reevaluaciones desde los servicios del backend.
2. **Presupuesto:** se propone POST para crear el único presupuesto del período y PUT para actualizarlo, evitando que existan presupuestos duplicados.
3. **Restauración:** el contrato exige `confirmed: true`, pero la validación de integridad y la protección de los datos actuales seguirán siendo responsabilidad del backend.



## 9.1 Decisiones contractuales del Bloque 2

Las siguientes decisiones se aprobaron durante el refinamiento de API-001. Se distinguen de las decisiones históricas de negocio y de las reglas ya establecidas en SPEC-003, DATA-001 y UI-001.

| Decisión | Resolución |
|---|---|
| API-DEC-009 | La alerta Próxima se genera cuando faltan 24 horas o menos para el inicio y la actividad aún no ha comenzado. |
| API-DEC-010 | La evaluación de alertas se limita al período seleccionado. |
| API-DEC-011 | La consulta normal de alertas incluye registros con condición activa e inactiva; se puede filtrar mediante `condition_active`. |
| API-DEC-012 | El historial se devuelve embebido en cada alerta mediante `history`. |
| API-DEC-013 | Marcar como revisada es idempotente: una alerta ya Revisada no recibe otro evento de revisión ni cambia su timestamp. |
| API-DEC-014 | El rango de calendario incluye ambos extremos; se incluyen actividades cuyo rango de fechas intersecta el solicitado. |
| API-DEC-015 | Una actividad multidiaria se devuelve una sola vez en la respuesta del calendario, aunque se represente en varios días en el frontend. |

Las decisiones históricas DEC-022 a DEC-027 y las decisiones de presentación DP-CAL-001 a DP-CAL-003 resueltas en UI-001 permanecen vigentes sin modificación. Las reglas de tipos, estados, condiciones, historial y eliminación de alertas de SPEC-003 y DATA-001 tampoco se alteran.
