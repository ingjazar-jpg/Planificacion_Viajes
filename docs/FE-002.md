## 1. Objetivo

Implementar el Dashboard del período seleccionado y la experiencia de consulta y revisión de alertas, consumiendo exclusivamente los contratos backend existentes. La interfaz presentará indicadores y gráficos comprensibles, un contador de alertas pendientes y activas, y un panel accesible para consultar y revisar alertas.

El frontend no duplicará reglas de negocio ni cálculos financieros, de cumplimiento, vencimiento o evaluación de alertas.

## 2. Contexto y restricciones

1. FE-001 está validado y cerrado. Se reutilizarán el shell, Topbar, contexto global de período, cliente HTTP, estados comunes y navegación existentes.
2. El backend BE-006 y BE-009 está validado.
3. GitHub en la rama `feat/backend-domain-foundation` es la fuente de verdad del código y documentación.
4. No se modificarán API-001, SPEC-003, SPEC-005 ni los contratos backend para resolver necesidades de presentación.
5. No se añadirán dependencias de gráficos ni de estado. Los gráficos se implementarán con SVG y CSS nativos.
6. No se incorporarán Redux, Axios, servicios externos, notificaciones externas, temporizadores ni sondeos periódicos.
7. No se mostrarán cifras, actividades ni alertas ficticias.

## 3. Alcance

### 3.1 Incluido

- Dashboard del período global seleccionado.
- Indicadores financieros y de actividades.
- Cuatro gráficos contractuales.
- Estados de carga, error, reintento y vacío.
- Evaluación de alertas al entrar por primera vez en un período durante la sesión.
- Consulta de alertas pendientes y con condición activa.
- Contador de la campana de Topbar.
- Drawer de alertas en escritorio y móvil.

- Marcado de alerta como revisada.
- Navegación desde una alerta a la sección Actividades, conservando su `activity_id` como contexto de destino.
- Accesibilidad y adaptación responsive.
- Pruebas unitarias, de componentes e integración del alcance.

### 3.2 Excluido

## 6. Contratos de integración

### 6.1 Dashboard

- Método: GET.
- Ruta: `/api/v1/periods/{period_id}/dashboard`.
- Backend: BE-009.
- No admite filtros ni paginación.
- La respuesta se consume según API-001 §5.7.
- El objeto `data.financial` alimenta indicadores financieros.
- El objeto `data.activities` alimenta indicadores de actividades.
- El objeto `data.alerts` alimenta los tres contadores de alertas del resumen.
- El objeto `data.charts` alimenta los cuatro gráficos.

El frontend no sumará `upcoming_pending`, `overdue_pending` y `high_priority_pending` para construir el contador de campana, porque una actividad puede tener alertas de más de un tipo. El contador se obtiene del listado filtrado de alertas.

### 6.2 Evaluación de alertas

- Método: POST.
- Ruta: `/api/v1/alerts/evaluate`.
- Request: `{ "period_id": "UUID" }`.
- Backend: BE-006.
- Se limita al período seleccionado.
- La respuesta y sus errores respetan API-001 §5.4.
- La evaluación no modifica el estado de las actividades.

La evaluación y la consulta del Dashboard son responsabilidades independientes: un fallo de evaluación no debe impedir que el Dashboard intente cargar sus indicadores. Sin embargo, si la evaluación falla, el frontend no presentará el listado de alertas como actualizado. El panel de alertas mostrará el error de evaluación y permitirá reintentarla.

### 6.3 Consulta de alertas

- Método: GET.
- Ruta: `/api/v1/alerts`.
- Backend: BE-006.
- Parámetros obligatorios para este uso: `period_id`, `status=Pendiente`, `condition_active=true`.
- No enviar `page` ni `page_size`: API-001 devuelve el conjunto completo filtrado.
- Cada alerta contiene `id`, `activity_id`, `type`, `status`, `condition_active`, `activity` y `history`.
- Para la interfaz se usarán los campos de `activity` definidos en API-001; no se harán consultas individuales adicionales para reconstruir la alerta.

### 6.4 Marcar como revisada

- Método: PATCH.
- Ruta: `/api/v1/alerts/{alert_id}/review`.
- Sin cuerpo.
- Backend: BE-006.
- Respuesta HTTP 200 con la alerta actualizada.
- La operación es idempotente.
- No modifica `condition_active` ni el estado de la actividad.

El frontend actualizará localmente el conjunto visible después de recibir una respuesta exitosa. Si la solicitud falla, conservará la alerta en pantalla y mostrará un error con opción de reintento.

## 7. Flujo de carga y actualización

### 7.1 Primera entrada a un período durante la sesión

1. Leer `selectedPeriodId` del contexto FE-001.
2. Si no existe período seleccionado, mostrar estado vacío contextual y no llamar endpoints que requieran UUID.
3. Consultar el Dashboard mediante GET.
4. Comprobar en memoria si el período ya fue evaluado durante la sesión.
5. Si no fue evaluado, ejecutar POST de evaluación.
6. Si la evaluación tiene éxito, registrar el período como evaluado en memoria y consultar GET de alertas filtradas.
7. Si la evaluación falla, mostrar error únicamente en el área de alertas; no presentar el listado como actualizado.
8. Si la consulta de Dashboard falla, mostrar su error y reintento independientemente del estado de alertas.

### 7.2 Cambio de período

- Cambiar el período invalida los datos visibles del período anterior para evitar mezclar información.
- Se solicita el Dashboard del nuevo período.
- Si el período nunca fue evaluado durante la sesión, se evalúa antes de consultar su listado de alertas.
- Si ya fue evaluado durante la sesión, se consulta nuevamente el Dashboard y el listado sin repetir POST.

### 7.3 Regreso al Dashboard desde otra sección

- Se vuelve a consultar Dashboard y alertas para reflejar cambios efectuados desde otras secciones.
- No se repite POST de evaluación si el período ya fue evaluado durante la sesión.
- Los datos anteriores no se presentan como actuales mientras la actualización está pendiente o ha fallado.

### 7.4 Revisión de alerta

1. Deshabilitar temporalmente la acción de esa alerta para evitar envíos simultáneos.
2. Ejecutar PATCH.
3. Si tiene éxito, retirar la alerta del conjunto visible y actualizar el contador.
4. Mostrar confirmación breve.
5. Si era la última alerta, mostrar el estado vacío aprobado sin cerrar el drawer.
6. Si falla, conservar la alerta y mostrar error/reintento.

## 8. Presentación visual

### 8.1 Indicadores

Grupo financiero:
- Presupuesto general.
- Total de gastos.
- Saldo general.
- Porcentaje de ejecución.

Grupo de actividades:
- Total de actividades.
- Distribución por estado.
- Cumplimiento.
- Actividades vencidas.

Los importes se presentarán en COP, respetando los valores decimales recibidos. El frontend no modificará ni redondeará los valores fuente.

### 8.2 Gráficos

| Componente | Datos API | Representación |
|---|---|---|
| `ActivityStatusChart` | `charts.activities_by_status` | Dona SVG, leyenda y cantidades. |
| `BudgetComparisonChart` | `charts.budget_vs_expenses_by_category` | Barras SVG agrupadas por categoría. |
| `ExpenseCategoryChart` | `charts.expenses_by_category` | Barras SVG por categoría. |
| `ComplianceIndicator` | `charts.completion_percentage` | Indicador circular SVG. |

Los gráficos tendrán títulos accesibles, etiquetas textuales, leyendas cuando correspondan y una alternativa de datos legible por tecnologías de asistencia. El significado de cada serie no dependerá exclusivamente del color.

### 8.3 Drawer de alertas

- Escritorio: panel lateral deslizable.
- Móvil: panel de pantalla completa.
- Se abre desde la campana de Topbar.
- Se cierra mediante control visible y tecla Escape.
- El foco se mueve al panel al abrirse, permanece contenido mientras esté abierto y regresa al control que lo abrió al cerrarse.
- El panel expone semántica accesible de diálogo/modal y nombre accesible.
- Grupos en orden Vencidas, Próximas, Prioridad alta.
- Dentro de cada grupo, fecha/hora de inicio ascendente.
- Si un grupo no contiene alertas, no se renderiza como grupo vacío.
- Si no hay alertas en ningún grupo, se muestra el estado vacío aprobado.

### 8.4 Contador

- El contador representa registros de alerta, no actividades únicas ni suma de contadores por tipo del Dashboard.
- Se actualiza con el resultado del listado completo filtrado.
- Después de revisar una alerta, disminuye en una unidad si la alerta pertenecía al conjunto mostrado.
- Si el total es cero, la campana no mostrará un número positivo.
- El botón tendrá nombre accesible que comunique la cantidad de alertas pendientes.

## 9. Estados y errores

### 9.1 Dashboard

- Carga: estado visual de carga en el área del Dashboard.
- Error: mensaje comprensible y acción Reintentar.
- Éxito: indicadores y gráficos del período consultado.
- Vacío de actividades: mensajes informativos en gráficos de actividades y cumplimiento 0 %.
- Período sin presupuesto: valores de presupuesto cero y gastos reales, si existen.
- Sin gastos: importes cero en gráficos financieros.

### 9.2 Alertas

- Evaluación pendiente: estado de carga en panel/contador; no mostrar datos previos como actuales.
- Evaluación fallida: error con acción para reintentar evaluación.
- Consulta fallida: error con acción para reintentar consulta, sin bloquear Dashboard.
- Carga correcta sin alertas: estado vacío aprobado.
- Revisión en curso: acción de la alerta correspondiente deshabilitada temporalmente.
- Revisión fallida: alerta permanece visible y se ofrece reintento.
- Revisión exitosa: confirmación breve y actualización del listado/contador.

No se expondrán trazas, rutas físicas, mensajes internos ni detalles técnicos sensibles del backend.
